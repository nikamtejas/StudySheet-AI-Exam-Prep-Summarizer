# StudySheet — CLAUDE.md

AI exam-prep PDF summarizer. Full spec: `docs/studysheet-build-prompt.md`. Build order and
per-milestone gates: `docs/studysheet-milestones.md`. Read both before touching a milestone you
haven't worked on yet — this file is the rules, those are the requirements.

## Current milestone

**M0 — Foundations: done.** Both folders build, lint, typecheck, and test independently from a
clean clone; contracts sync + drift-check wired into CI; `/health` on api and worker checks
Mongo/Redis/storage; env is Zod-validated at boot in both folders.

**M1 — Ingest and probe: done.** Presign → upload → register flow (`POST /api/uploads/presign`,
`POST /api/documents`); per-page probe (text layer, char density, rotation, language via
`franc-min`) in `src/pipeline/probe.ts`; MIME-sniffed/size/page-count/encrypted validation in
`src/pipeline/validate.ts`; vision-path rasterization via poppler's `pdftoppm` (150 DPI, JPEG q80)
in `src/pipeline/rasterize.ts`; hash-based dedup on `Document` (`{userId, fileHash}` unique index,
race-safe); `npm run probe -- <path>` CLI. Synthetic fixtures for every required case (typed,
scanned-handwritten, slides, mixed, encrypted, corrupt, zero-text-layer, rotated, 100-page stress)
in `backend/fixtures/pdfs/`, generated by `backend/fixtures/generate.mjs`.

Local system deps this milestone added (dev machine, not just npm): **poppler** (`pdftoppm` —
rasterization) and **qpdf** (one-time use, to generate the encrypted fixture). `brew install
poppler qpdf`. CI installs `poppler-utils` via apt and brings up real Mongo + MinIO service
containers so `test/ingest.test.ts` runs for real there; locally it skips gracefully (with a
console warning) if Mongo/storage aren't reachable, so `npm test` still passes without Docker
running.

pdfjs-dist is used for structural analysis only (page count, text content, rotation) — never for
rendering. Its Node canvas-rendering path hit two separate compatibility bugs (`@napi-rs/canvas`:
broken glyph fill; `canvas`: broken image-XObject draw) during M1, so rasterization goes through
poppler instead. Don't reintroduce `page.render()` on pdfjs-dist without re-verifying that.

**M2 — The pipeline skeleton and the text path: done.** Full text-path pipeline:
`pipeline/extract.ts` (line/font reconstruction from pdfjs text items) → `pipeline/prepare.ts`
(strips repeated headers/footers/page numbers by cross-page line repetition) →
`pipeline/chunk.ts` (8–15 pages or ~15k estimated tokens, 1-page overlap, cuts early at a detected
heading once the 8-page minimum is met) → `pipeline/map.ts` (one Sonnet 5 call per chunk, strict
JSON) → `pipeline/reduce.ts` (dedup by normalized text, rank by mention count — pure, no AI call)
→ `pipeline/synthesize.ts` (one Opus 4.8 call with adaptive thinking, produces the final sections/
definitions/examQuestions). `pipeline/orchestrate.ts`'s `processJob()` drives all of this against
a `Job` document (`src/models/Job.ts`) that persists every stage's output — chunk-by-chunk, saved
after each one — so re-entering `processJob()` after a crash skips whatever's already recorded and
never re-bills a completed chunk (proven in `test/orchestrate.test.ts` against real Mongo, not just
mocked). `ai/client.ts` wraps the Anthropic SDK: model routing (`claude-haiku-4-5` /
`claude-sonnet-5` / `claude-opus-4-8` — **not** "claude-opus-5", which the spec's illustrative text
names but doesn't exist), structured outputs via `output_config.format` (JSON schema built with
`zod-to-json-schema`, not the SDK's own `zodOutputFormat` helper — that needs zod v4, we're pinned
to v3), a one-shot repair retry on validation failure, and real per-call cost accounting from
`usage`. BullMQ wired end-to-end: `worker/queue.ts` + `worker/processors/summarize.ts` call the
same `processJob()`. CLI: `npm run summarize -- <path> [--depth crash|balanced|deep]` — creates a
`Job` directly at `stage: "chunking"` (skips the Document/storage round trip since the file's
already local) and writes `<file>.summary.json`.

**No Anthropic API key is configured yet** (user's choice at M2 kickoff — see memory). Every

**M3 — Vision path: done.** Handwritten/slides/mixed pages now go through the same pipeline as
typed text. `ai/client.ts` generalized to a single `callStructured` that routes to
`anthropic.beta.messages.create` (the Files API beta, `files-api-2025-04-14`) whenever the user
content includes an image block, and to the plain GA `anthropic.messages.create` otherwise — the
two request shapes are typed as separate branches (the GA `ImageBlockParam.source` type doesn't
accept `{type:'file', file_id}`, only base64/URL, so one shared object across both calls doesn't
typecheck). `uploadFile`/`deleteFile` wrap `anthropic.beta.files.upload/delete`; pages are always
referenced by `file_id`, never re-sent as inline base64. `pipeline/chunkVision.ts` batches
vision-eligible pages into ≤20-page groups (also capped on raw byte size as a safety margin) with
no overlap — a 100+ page document just produces more batches. `pipeline/mapVision.ts` uploads each
batch's pages, calls the model once per batch with `confidence: 'low'` on uncertain transcriptions
and `unreadablePages` for illegible ones, then deletes the uploaded files in a `finally` (cleaned
up even on failure). `pipeline/orchestrate.ts`'s mapping stage now runs two loops — text chunks,
then vision chunks — over the *same* `chunkResults` array and the *same* already-done check;
vision chunk indices are assigned to continue directly after the text chunk indices
(`job.chunks.length + i`, see `models/Job.ts`), which is what lets one resumability mechanism cover
both kinds without duplicated logic. `pipeline/synthesize.ts` surfaces `unreadablePages` in the
page-map section so a gap is visible, never silently dropped. CLI: rasterizes and uploads
vision-path pages to real storage locally (`cli-local/{fileHash}/pages/{n}.jpg`) before creating
the Job, since the orchestrator always resolves vision buffers via `downloadObject(rasterKey)` —
this is the one case where the CLI needs MinIO/R2 reachable even though the source PDF itself
never round-trips through the `Document` model.

Vision-path resumability (text chunk done + vision batch crashes mid-run, and vice versa) is
covered in `test/orchestrate-vision.test.ts` against real Mongo, with a mocked Anthropic SDK and a
mocked `downloadObject` — same "mock-tested only" pattern as M2, no API key required. That file and
`test/orchestrate.test.ts` intentionally use disjoint `userId` prefixes (`test-text-orch-` /
`test-vision-orch-`) for their `afterAll` cleanup regexes: vitest runs test files in parallel
worker processes against the same real database, and a shared broad prefix (`test-*`) let one
file's cleanup delete another file's still-in-flight job, surfacing as a Mongoose `VersionError`.
If adding another real-Mongo test file, give it its own disjoint prefix too.

**M4 — Solve and verify: built, gate not yet run for real.** Problems detected during M2's reduce
stage (`ChunkProblem[]`, already deduped) now get solved and independently verified.
`pipeline/solve.ts`'s `solve(statement)` is one Sonnet 5 call (adaptive thinking on) producing the
full `SolvedProblemSchema` JSON from `contracts/problem.ts` — `given`/`goal`/`strategy`/`steps`
(each with a **required** `why`)/`answer`/`check`/`commonMistake`/`memoryHook`, plus an optional
`visual: VisualSpec`. `pipeline/verify.ts`'s `solveOne(problem)` is the verified, resumable entry
point (also the standalone function M7's paste/photo single-problem flow will call directly):
it fires two independent `solve()` calls in parallel that never see each other's output, compares
final answers with `answersAgree()` (numeric-aware — mathjs `evaluate()` so "1/2" and "0.5" agree;
mathjs unit conversion so "5 m/s" and "18 km/h" agree; a genuine dimensional mismatch, e.g. "5 m"
vs "5 s", fails outright even if the bare numbers match), and on disagreement runs a third attempt
and takes the majority. All three disagreeing never drops the problem — it comes back
`verified: false` with a visible `verificationNote`, full solution intact (reliability invariant
5). `NUMERIC_TOLERANCE` is deliberately loose (0.5%, not float-equality): two *correct* independent
solves of an irrational-answer problem (a pendulum period, say) will round their displayed answer
differently, and that's not a disagreement worth escalating over.

`pipeline/orchestrate.ts` gained a `'solving'` stage between `'reducing'` and `'synthesizing'`:
problems run concurrency-capped (`SOLVE_CONCURRENCY = 4`) in batches — real parallelism for the
model calls (never sequential, never batched into one call, per spec), but persisted once per
*batch* rather than once per problem, so concurrent `job.save()` calls never race on the same
in-memory Mongoose document. A crash mid-batch loses at most that batch's in-flight problems, never
an already-persisted one — proven in `test/orchestrate-solve.test.ts` (own disjoint `userId`
prefix, `test-solve-orch-`, per the cross-file cleanup-race lesson from M3). `Job` gained
`problems`/`problemResults`; `Summary` gained a `problems: VerifiedProblem[]` field (stored as one
Mixed blob, like `Job.reduced` — Mongoose's TS types reject `[Schema.Types.Mixed]` against a
strongly-typed array field, but accept a bare `Schema.Types.Mixed`, and it round-trips as a real
array at runtime regardless).

`VisualSpec` (`contracts/problem.ts`) is typed as the full ten-kind discriminated union from
docs/studysheet-build-prompt.md §4, but nested per-kind shapes (geometry shapes, tree nodes,
flowchart nodes/edges) are deliberately loose (`z.unknown()`) — M5 "Visual primitives" owns the

Nothing renders a `VisualSpec` yet; M4's job was only to constrain the model to one of the ten

**M5 — Visual primitives: done.** First milestone touching `frontend/`. All ten `VisualSpec` kinds
from docs/studysheet-build-prompt.md §4 render as server-only React SVG components under
`frontend/src/components/visuals/` (`FunctionPlot`, `NumberLine`, `Geometry`, `VectorDiagram`,
`Flowchart`, `Tree`, `Grid`, `Timeline`, `Cycle`, `Compare`) — no `"use client"`, no hooks, no
animation, so they render identically inside a Puppeteer print pass with zero hydration.
`backend/src/contracts/problem.ts`'s `VisualSpecSchema` was tightened from M4's placeholder
`z.unknown()` fields to real typed shapes (geometry shapes/labels/angles/congruence marks,
flowchart nodes/edges, a recursive `TreeNode` via `z.lazy()`, grid rows/highlight cells, cycle
stages, compare sides) and re-synced to frontend; confirmed `zod-to-json-schema` handles the
recursive `z.lazy()` correctly (produces a `$ref`, doesn't throw) before relying on it for M4's
`solve()` structured output.

**Malformed input is caught by calling components as plain functions, not JSX.** `Visual.tsx`'s
dispatcher (`FunctionPlot({ spec })`, not `<FunctionPlot spec={spec} />`) runs each component's
body immediately inside a `try/catch` — JSX alone just builds a lazy element descriptor that
React doesn't actually invoke until later, outside any surrounding `try/catch`, so this direct-call
pattern is what makes "invalid spec → drop the visual, keep rendering everything else" actually
work. `VisualSpecSchema.safeParse()` runs first as a second line of defense. Confirmed both layers
work via `Visual.test.tsx` (unrecognized `kind`, `null`, and schema-valid-but-degenerate input like
a zero-width `functionPlot` domain — all render nothing, never throw) and manually in a live
browser (`/dev/gallery`'s "Malformed input" section).

Arrows (`vectorDiagram`, `flowchart`, `cycle`) are drawn as inline computed polygons
(`visuals/arrow.ts`), not SVG `<marker>` defs — marker `id`s are shared per-document, so two
instances of the same component on one page (e.g. two flowcharts, or the gallery rendering
everything at once) would collide on a static id.

KaTeX server-rendering helper (`frontend/src/lib/katex.ts`, `renderInlineMath`/`renderDisplayMath`)
+ thin `<InlineMath>`/`<DisplayMath>` wrapper components (`frontend/src/components/Math.tsx`), both
server-only. Minimal "Marker" palette color tokens (ink/surface/edge/paper/amber/teal/muted) added
to `frontend/src/app/globals.css` via Tailwind v4's `@theme` block — **fonts, the type scale, and
the rest of the app shell are deliberately not built yet**, that's M7 ("Web app"). The three-rung
solve ladder (Worked/Guided/Practice) from §4's narrative text is still not built, same as M4 —
still not listed as any milestone's deliverable.

`/dev/gallery` (noindex via metadata, never linked from app nav) renders all ten primitives with
sample data (`visuals/sampleSpecs.ts`, shared with the snapshot tests so both exercise identical
data) in three presentations — normal, greyscale (`filter: grayscale(1)`, proving weight/dash carry
meaning without color), and print (paper background) — plus the KaTeX helper and the
malformed-input section. Manually verified in a real browser, not just asserted by tests.
`Visual.test.tsx` snapshot-tests all ten via `react-dom/server`'s `renderToStaticMarkup` (no
`@testing-library/react` needed for pure prop-in/markup-out server components) and asserts
byte-identical output on repeat render — the prerequisite for M6's "same JSON in → byte-comparable
PDF out" gate.

**M6 — PDF renderer: done.** The split architecture proves itself here: `frontend/` owns
`/print/[summaryId]` (three variants — full study sheet, one-pager, answer appendix — via
`?variant=`), `backend/` just drives a headless browser at it. Frontend's `app/` was restructured
into two route groups — `(app)/` (the existing landing page, now with its own `layout.tsx`) and
`(print)/` (a second, independent root layout, Next.js's documented "multiple root layouts"
pattern) — because `/print` needs a completely separate `<html>`/`<body>` shell with zero app
chrome, and a page nested under a shared root layout can't override that root's own tags.

**Render tokens**: HMAC-SHA256, single-use, ~2min TTL, scoped to one summary id
(`backend/src/lib/renderToken.ts` signs with `node:crypto`; `frontend/src/lib/renderToken.ts`
independently verifies the same scheme with Web Crypto, since Next.js Middleware runs on the Edge
runtime — no `node:crypto`, no `Buffer`. Confirmed the two crypto APIs produce byte-identical
HMAC output for the same secret+payload before relying on this). `frontend/src/middleware.ts`
gates `/print/:path*`: a forged or expired token gets a real HTTP 403 before the page ever renders
— this is the one thing a `page.tsx` genuinely cannot do on its own (App Router pages have no way
to set an arbitrary status code), so Middleware is load-bearing here, not incidental. Single-use
itself is enforced only at the backend's `GET /api/render/:summaryId` (the DB check middleware
can't do statelessly) — an already-consumed token surfaces as 404 via the page's own `notFound()`,
one layer softer than forged/expired's 403, and that's an accepted, intentional gap (see memory).

**Puppeteer**: cold Chromium launch measured at ~7.8s on this machine — confirms the milestone's
own warning almost exactly, and is why a warm pool (`backend/src/lib/puppeteerPool.ts`,
`PUPPETEER_POOL_SIZE`) isn't optional. Warm-pool render measured end-to-end (navigate → wait for
`data-render-ready` → `page.pdf()`) at 130–450ms real, ~15x under the 3s budget, including the
KaTeX-heavy answer-appendix variant and the Next.js App Router page's own baseline client JS (see
below). `closePuppeteerPool()` is wired into the API server's `SIGTERM`/`SIGINT` handlers — the
one thing here that leaks real OS processes if the process dies without closing it explicitly.

**Byte-comparability required a real fix, not just "don't add timestamps."** Confirmed directly:
two `page.pdf()` calls from Puppeteer for *identical* HTML content are NOT byte-identical — some
Chromium-internal serialization detail varies run to run, with no visible cause (no `/CreationDate`
or `/ModDate` present either). Re-serializing the output through `pdf-lib` (normalized
creation/mod dates, blanked producer/creator/author/subject/title, `useObjectStreams: false` for a
deterministic object layout) makes two independently-generated PDFs of the same content
byte-identical — also confirmed directly, and now what `pipeline/render.ts`'s `canonicalize()`
does before every upload. Without this step, "same JSON in → byte-comparable PDF out" would
silently fail despite every other part of the pipeline being deterministic.

**"Zero client JS" is aspirational, not literal, for `/print` — a measured, considered
tradeoff.** Next.js App Router ships a baseline shared JS bundle (~113KB, React + the Next.js
runtime) for every route by default, including one with zero `"use client"` components — there is
no simple App Router flag to suppress it; genuinely zero bytes would mean abandoning `page.tsx`
for a raw Route Handler that manually strings together HTML (losing JSX/component reuse, including
M5's visual components). Given the *functional* intent — no hydration, no client component
overhead — is already met, and the real, measured impact is negligible (component renders in
130–450ms end-to-end, nowhere near the 3s budget), keeping the current `page.tsx` implementation
was the pragmatic call. If bundle size becomes a real constraint later, the raw-Route-Handler
rewrite is the documented escape hatch — see memory for detail.

**One-pager "fits on exactly one sheet" is a real measure-and-retry loop**, not a fixed content
budget: `pipeline/render.ts`'s `renderSummary()` renders, checks the actual page count via
`pdf-lib`, and if it's more than one page, increments a `trimLevel` and re-renders — up to a bound
— never shrinking type below the print CSS's floor. `frontend/.../OnePager.tsx` owns the actual
priority order content gets dropped in (definitions and formulas are the bulk of the value; only
the top 3 exam questions are offered at all, per §5's own description) — the backend's retry loop
only drives *how many* items to drop, never *which*.

**Highlight cap** (§6: "if more than ~15% of a page is marked, drop the weakest marks") is
enforced in `backend/src/pipeline/highlightCap.ts`, applied only in the render-fetch path
(`GET /api/render/:summaryId`) — never touches the persisted `Summary`, so a future interactive
web preview (M7) can still show every highlight. "Weakest" isn't spec-defined: `definition` marks
drop before `exam-critical` ones, and within a kind, longer highlighted spans drop before shorter
ones — a documented judgment call, not a spec requirement.

**Known gap, not yet done:** CI currently runs backend and frontend as fully separate jobs with no
shared network, so `backend/test/render.test.ts` (which needs a real reachable frontend server, not
just Mongo/MinIO) will skip gracefully in CI exactly like it does locally — its assertions have
only been verified by hand this session (real Puppeteer, real timing, real byte-comparison, real
page counts — see memory for the specific numbers), never by an automated CI run. Wiring CI to
build+start a live frontend alongside the backend job is the natural next step for whoever picks
this up, but was deliberately left undone here rather than risk an unverifiable, blast-radius-large
CI change with no way to confirm it actually works from this environment.

**M7 — Web app: done.** Landing, upload, processing, preview, and standalone-solve routes under
`frontend/src/app/(app)/`, backed by three new backend surfaces: `POST /api/jobs` +
`GET /api/jobs/:id` + `GET /api/jobs/:id/stream` (SSE), `POST /api/solve`, and
`GET /api/summaries/:id` + `GET /api/summaries/:id/source`.

**SSE is Mongo-polling, not pub/sub.** `jobs.ts`'s stream handler polls `JobModel.findById` every
500ms; the worker (a separate process) is the only writer, and it already checkpoints every stage
(M2's reliability invariants), so Mongo is already the single source of truth regardless of which
process is asking. That's what makes "resumes without duplicate sections" (the M7 gate) free: a
fresh connection just starts polling current state and reports forward — there's no event history
to replay, so there's nothing to duplicate. The dedup-by-content and terminal-event logic is
extracted into `backend/src/pipeline/sseSnapshot.ts` (`computeSseSnapshot` / `snapshotChanged` /
`isTerminal`) specifically so it's unit-testable without a live HTTP/EventSource harness — same
pattern as `pipeline/jobProgress.ts` (`computeJobProgress`, extracted from a private helper in
`jobs.ts` for the same reason). Neither route file has dedicated HTTP-level tests; the codebase's
established convention is testing pipeline/logic functions directly rather than introducing
`supertest` as a new pattern, so route wiring itself is verified by manual `curl`/live-server smoke
tests, not automated ones.

**Real bug found via live smoke-testing, not caught by any unit test:** no route in `src/api/`
ever called `getMongoConnection()` — only CLI entry points and test setup did. Mongoose model
calls buffer against whatever connection `mongoose.connect()` eventually produces, but nothing
ever called that in the live API process; it only worked by accident, whenever some earlier
request happened to hit `GET /health` first (which calls it via `checkMongo()`) and warmed the
shared connection as a side effect. The first real request to land on a cold server that wasn't
`/health` sat in Mongoose's buffer for a full 10s and then 500'd — confirmed directly (10013ms,
`MongooseError: buffering timed out`) by curling `/api/jobs/:id/stream` against a freshly started
server before anything else had hit it. Fixed with `backend/src/api/middleware/ensureMongo.ts`
(`ensureMongoConnected`), mounted on `app.use('/api', ...)` — after `/health` (which keeps its own
already-correct graceful-degradation behavior) but before every data route. Confirmed the fix:
same cold-start sequence now returns the correct 404 in 36ms.

**RSC boundary lesson (preview route):** a Client Component must never import a Server Component
that pulls in server-only weight — doing so drags that weight into the client bundle even though
the component never runs client-side logic. Hit this directly: an early version had a `'use
client'` orchestrator import `SummaryPane` (which uses M5's `Visual`/`InlineMath`, pulling in
mathjs + KaTeX), and the preview route's first-load JS came out to ~393KB. Fixed via a Context
architecture — `PreviewProvider` (client) holds shared state (`activePage`, `highlightsVisible`);
`SummaryPane` stays a pure Server Component with no client-state props; small client "islands"
(`PageRefButton`, `HighlightToggle`, `HighlightScope`) consume context from inside server-rendered
content; the route itself is an async Server Component fetching data server-side. Bundle dropped
to 116KB. If a future milestone touches `frontend/src/components/preview/`, preserve this
direction — Server Component importing Client Component is fine, the reverse isn't (when the
Server Component has server-only deps).

**Bundle-size budget is enforced, not just measured.** `frontend/scripts/check-bundle-size.mjs`
reads `.next/app-build-manifest.json`'s `/(app)/page` entry, gzips each referenced `.js` chunk, and
fails above 120KB — wired as `npm run check-bundle-size` and as a CI step right after `npm run
build` in the frontend job. Landing measures ~112KB gzipped by this script (Next's own "First Load
JS" report says 115KB — the two measure slightly differently, both comfortably under budget).

**Accessibility: verified structurally, not with a live browser or Lighthouse.** The Claude-in-Chrome
extension was unavailable for the entire session (same as M5/M6), so this was checked by reading
rendered HTML and source rather than in an actual browser: semantic form controls throughout
(`<fieldset>`/`<legend>` grouping the upload depth radios, `sr-only` `<label for>` on the file input
and the solve textarea, native `<input type="checkbox">` for the highlight toggle), every
interactive handler on a native `<button>` (no `onClick` on a `div`/`span` anywhere), focus-visible
rings on every interactive element sampled, `aria-live="polite"` + `role="status"` on
`ProcessingView`'s progress text, and the M5 SVG primitives' `viewBox`-only sizing (no `width`/
`height` attributes) which lets them shrink to their container naturally. One real gap this caught:
`SourcePane`'s pdf.js canvas rendered at a fixed `scale: 1.3`, wider than a 375px viewport with no
way to shrink — fixed with a `ResizeObserver` that renders at `min(containerWidth / pageWidth,
1.5)` instead, so it now fits any container width and reflows on resize. Lighthouse ≥95 and
axe-core-style automated a11y auditing were not run — no tooling for either was available in this
environment; flagging this explicitly rather than claiming a pass that wasn't actually checked.

## Folder map

```
studysheet/
├── frontend/            Next.js 15 (App Router) + React 19 + TS — UI *and* all PDF/preview rendering
├── backend/              Express API + BullMQ worker (one codebase, two npm scripts, two processes)
├── docker-compose.yml    Mongo, Redis, MinIO (local stand-in for Cloudflare R2)
├── docs/                 the build-prompt spec + the milestone plan
└── Makefile              make dev / verify / test — drives both folders from the root
```

Two independent Node projects. Separate `package.json`, separate lockfile, separate deploy. No
workspaces, no shared package linking, no path aliases crossing the folder boundary.

- `frontend/` has **no business logic and no database access** — it talks to the backend over
  HTTP through `frontend/src/lib/api.ts` only (added in M7), and never imports backend code.
- `backend/src/contracts/` is the **source of truth** for every Zod schema. Run
  `npm run sync:contracts` (in `backend/`) to copy it into `frontend/src/contracts/`. That copy
  is generated — the header says so — never hand-edit it, never define the same type twice.
- The PDF is produced by the frontend's `/print/[summaryId]` route (server-rendered, zero client
  JS); the backend's Puppeteer worker just navigates to it and calls `page.pdf()`. One
  implementation of every visual, two surfaces. Arrives in M5/M6.

## Commands

Run from the repo root:

```
make install    # npm install in both folders
make dev        # api + worker + frontend dev servers together
make verify     # lint + typecheck + test in both folders — this is the CI gate, runnable locally
make up / down  # docker compose for Mongo/Redis/MinIO
```

Or per folder: `npm run dev:api` / `npm run dev:worker` / `npm run dev` (frontend),
`npm run verify`, `npm run lint`, `npm run typecheck`, `npm run test`.

## Reliability invariants — violating any of these is a bug even if tests pass

1. No AI call in a request/response cycle. Ever. Everything model-touching runs in the worker.
2. Every pipeline stage is idempotent and independently resumable. Re-running a completed stage
   is free and produces identical output.
3. Every model call is wrapped: timeout, 3 retries with jittered backoff, and a typed failure
   that degrades the output instead of failing the job.
4. Every model response is parsed with Zod. On failure, retry once with the validation error
   appended; then fall back, never crash.
5. Partial failure degrades visibly — "pages 40–48 couldn't be read" printed in the output —
   never silently.
6. Intermediate JSON is persisted at every stage. Re-rendering, restyling, and regenerating
   derived artifacts must never re-run the model.
7. Money and quota move through one code path with reservation-then-commit semantics.
8. Every job records `costCents` and `tokensUsed`. Untracked spend is a production incident
   waiting to happen.
9. External input is untrusted: file type, size, page count, and text density are validated
   before a single token is spent.
10. Structured logs with a `jobId` on every line.

## Engineering rules

- TypeScript strict everywhere. `any` requires a comment explaining why (ESLint enforces this —
  `@typescript-eslint/no-explicit-any` is an error, not a warning, in both folders).
- Zod schemas live in `backend/src/contracts/`, synced into `frontend/src/contracts/` by script.
  Never hand-edit the frontend copy.
- Tests are written in the same commit as the code, not "later".
- No new dependency without a one-line justification in the PR description.
- Conventional commits, one commit per logical unit.
- Don't build ahead of the current milestone. Each milestone's doc says explicitly what *not* to
  build yet — that's deliberate sequencing, not an oversight.

## Env vars not required until later milestones

`env.ts` in both folders validates at boot, but a few vars are intentionally optional until the
milestone that wires them up makes them load-bearing, so M0–M1 dev doesn't require live keys:

- `ANTHROPIC_API_KEY` — optional until M2 (real Claude calls)
- `STRIPE_*` / `RAZORPAY_*` — optional until M10 (billing)

Everything else (Mongo, Redis, storage, `AUTH_SECRET`, `RENDER_TOKEN_SECRET` in both `backend/.env`
and `frontend/.env.local` — required as of M6, the two must match exactly — `FRONTEND_URL`/
`CORS_ORIGIN`, `NEXT_PUBLIC_API_URL`/`NEXT_PUBLIC_APP_URL`) is required now and
has no default — see `.env.example` / `.env.local.example` for the local dev values.
